# GMD 3.1.0 Polish Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the hand-patched Nashorn runtime with Rhino 1.9.1 and a reproducible, polyfill-free build, restore all 192 Highlight.js languages, stop guessing at languages that were never specified, and clear the review findings that accumulated around the 3.1.0 work.

**Architecture:** `highlightjs-jvm` swaps Nashorn for Rhino 1.9.1 — a single 1.6 MB jar that natively provides `Symbol`, `Map`, `Set`, `Object.assign`, arrow functions, template literals, destructuring and generators. Because those built-ins are present, the Highlight.js distribution needs only a **syntax-only** Babel transpile with **no polyfills and no hand-editing** — which is what made the previous Nashorn bundle unreproducible. `buildBundle.sh` concatenates a small prelude, the upstream core, all 192 upstream grammars and a 4-line wrapper, runs one stock `preset-env` pass over the result, and writes the committed bundle. The `javaHighlight` wrapper returns `null` when a language is unknown or absent, letting the Java layer simply skip those blocks.

**Tech Stack:** Java 21, Groovy 5.0.8, Maven 3.9.9+, JUnit Jupiter 6.1.2, Rhino 1.9.1 (`org.mozilla:rhino`), Highlight.js 11.7.0, Jsoup 1.23.1, PDFBox 3.0.7 (already present, used by one test). Node 18+ and Babel 7 are needed **only** to regenerate the bundle, never for a normal build.

## Background: what was measured

All figures measured on this repo with JDK 21 (`21.0.11+11-LTS`). Do not re-litigate them.

| approach | engine jars | build tooling | committed artifact | init (warm) | highlight | langs |
|---|---|---|---|---|---|---|
| Nashorn (status quo) | 2.5 MB | Babel + hand-patched shims | 152 KB, **not reproducible** | 384–1264 ms | ~160 ms | 14 |
| **Rhino 1.9.1 (chosen)** | **1.6 MB** | pinned Babel, **no polyfills** | 1.18 MB, reproducible | **182–287 ms** | **13–17 ms** | **192** |
| GraalJS 25.2.4 | 66 MB | none | none | 337–523 ms | 38–93 ms | 192 |
| core-js on Nashorn | 2.5 MB | Babel + core-js | 488 KB | **3644–5940 ms** | — | 20 |

**Why the old bundle could not be reproduced.** It was hand-patched after transpiling: a 3,053-byte hand-written prelude (`_Symbol`, `_Map`, `Set`, `Array.from`, `Array.prototype.includes/findIndex`, `String.prototype.startsWith/repeat/includes`, `Object.assign`) plus rewriting of Highlight.js's own `Symbol(` call sites to `_Symbol(` and `Map` to `_Map`. Reproducing that by regex is unsafe — the javascript grammar's built-in list contains the literal string `"Symbol"`, which a blind rename corrupts. Rhino removes the need entirely because it *has* those built-ins.

**What Rhino 1.9.1 cannot parse** (hence the syntax-only transpile): `class` declarations (8 in the Highlight.js core), rest parameters `function r(e,...t)`, call spread `f(...x)` (12 of 192 grammars), `for(const…of)` (1 grammar), and `\p{XID_Start}` unicode property regex (the python grammar). It *does* support `Symbol`, `Map`, `Set`, `Object.assign`, arrow functions, template literals, destructuring, object/array spread, optional chaining, generators, default parameters, regex lookbehind and named groups, and BigInt.

**Verified behaviours the implementation depends on:**
- A JS `null` return arrives in Java as literal `null`; a successful highlight arrives as `java.lang.String`.
- Rhino has **no** `console` (`typeof console === "undefined"`), so a feature-detected shim is included. All 192 grammars happened to load without it, but that is luck, not a guarantee.
- Unsynchronized concurrent use of one shared scope **corrupts Highlight.js state** — observed `JavaScriptException: Error: begin & end are not supported with match`. Synchronized: zero failures over 100 concurrent calls.
- `cx.setInterpretedMode(true)` is required; without it Rhino compiles to bytecode and a 1.18 MB script risks the 64 KB per-method limit.
- `cx.setLanguageVersion(Context.VERSION_ES6)` must be set **before** `initStandardObjects()` or `Symbol`/`Map`/`Set` are absent.
- Two consecutive Babel runs produce byte-identical output (sha256 stable), so "regenerate and diff" is a meaningful check.
- The exact `HighlightJsHighlighter` in Task 1 was compiled against Rhino 1.9.1 and run against the real bundle: all languages highlight, `text`/`plaintext` return escaped-only text, unknown/null/blank return `null`, HTML escaping is intact, and 100 concurrent calls produced 0 failures.

/*
 * The Java-facing entry point.
 *
 * Returning null means "leave this block alone": either no language was given,
 * or it is one Highlight.js does not know. Auto-detection is deliberately never
 * used - it mislabels prose and console output as code.

function javaHighlight(code, language) {
  if (!language) {
    return null;
  }
  if (!hljs.getLanguage(language)) {
    return null;
  }
  return hljs.highlight(code, { language: language, ignoreIllegals: true }).value;
}

- [ ] **Step 5: Add the build script**

Create `highlightjs-jvm/buildBundle.sh`, then `chmod +x highlightjs-jvm/buildBundle.sh`:

```bash
#!/usr/bin/env bash
#
# Regenerates src/main/resources/highlightJs/highlight.js for Rhino.
#
# Requires Node 18+. NOT part of the Maven build - run it by hand when the
# Highlight.js distribution changes, then commit the regenerated bundle.
#
#   ./buildBundle.sh            regenerate the bundle
#   ./buildBundle.sh --verify   regenerate to a temp file and diff against the
#                               committed one; non-zero exit means it is stale
#
# Rhino natively provides Symbol, Map, Set and Object.assign, so this is a
# syntax-only transpile with no polyfills and no hand-editing of any kind.
# The toolchain is installed with `npm ci` from the committed lockfile, so two
# runs produce byte-identical output.
set -euo pipefail

cd "$(dirname "$0")"
SRC="source/highlightJs"
BUNDLE="src/main/resources/highlightJs/highlight.js"

if [ ! -d "$SRC/languages" ]; then
  echo "Missing $SRC - the Highlight.js cdn-assets tree must be present" >&2
  exit 1
fi
if ! command -v node >/dev/null 2>&1; then
  echo "Node 18+ is required to regenerate the bundle; none found on PATH" >&2
  exit 1
fi
NODE_MAJOR="$(node -p 'process.versions.node.split(".")[0]')"
if [ "$NODE_MAJOR" -lt 18 ]; then
  echo "Node 18+ is required to regenerate the bundle; found $(node --version)" >&2
  exit 1
fi

# npm ci installs exactly what the lockfile pins and never rewrites it, which is
# what makes the output reproducible. The lockfile only has to be bootstrapped
# once, the first time this script is ever run.
if [ -f package-lock.json ]; then
  npm ci --no-audit --no-fund --silent
else
  echo "No package-lock.json yet - bootstrapping one. Commit it alongside the bundle." >&2
  npm install --no-audit --no-fund --silent
fi

WORK="$(mktemp -d)"
trap 'rm -rf "$WORK"' EXIT

# Deterministic order: our prelude, upstream core, every upstream grammar sorted
# by name under a fixed collation, then our wrapper.
{
  cat src/main/js/prelude.js
  echo ";"
  cat "$SRC/highlight.min.js"
  echo ";"
  for grammar in $(LC_ALL=C ls "$SRC"/languages/*.min.js | LC_ALL=C sort); do
    cat "$grammar"
    echo ";"
  done
  cat src/main/js/wrapper.js
} > "$WORK/raw.js"

./node_modules/.bin/babel --config-file ./babel.config.json \
  --compact true --no-comments "$WORK/raw.js" --out-file "$WORK/bundle.js"

if [ "${1:-}" = "--verify" ]; then
  if cmp -s "$WORK/bundle.js" "$BUNDLE"; then
    echo "OK: $BUNDLE matches a fresh build"
    exit 0
  fi
  echo "STALE: $BUNDLE differs from a fresh build. Run ./buildBundle.sh and commit." >&2
  exit 1
fi

mkdir -p "$(dirname "$BUNDLE")"
cp "$WORK/bundle.js" "$BUNDLE"
echo "Wrote $BUNDLE ($(wc -c < "$BUNDLE") bytes)"
```

```java
package se.alipsa.highlightjs;

import org.mozilla.javascript.Context;
import org.mozilla.javascript.Function;
import org.mozilla.javascript.Scriptable;
import org.mozilla.javascript.Undefined;

import java.io.IOException;
import java.io.InputStream;
import java.io.InputStreamReader;
import java.io.Reader;
import java.nio.charset.StandardCharsets;

/**
 * Highlight.js running on Rhino.
 *
 * The bundle is a syntax-only transpile of the upstream distribution; Rhino
 * supplies Symbol, Map, Set and Object.assign natively so nothing is polyfilled.
 * One scope is shared, and Highlight.js keeps mutable state in it, so calls are
 * synchronized - concurrent use corrupts that state.
 */
public final class HighlightJsHighlighter implements SyntaxHighlighter {

  private static final String RESOURCE = "/highlightJs/highlight.js";
  private static final String FUNCTION_NAME = "javaHighlight";

  private final Scriptable scope;

  public HighlightJsHighlighter() {
    Context cx = enterContext();
    try (InputStream input = HighlightJsHighlighter.class.getResourceAsStream(RESOURCE)) {
      if (input == null) {
        throw new IllegalStateException("Missing Highlight.js resource " + RESOURCE);
      }
      Scriptable created = cx.initStandardObjects();
      try (Reader reader = new InputStreamReader(input, StandardCharsets.UTF_8)) {
        cx.evaluateReader(created, reader, "highlight.js", 1, null);
      }
      if (!(created.get(FUNCTION_NAME, created) instanceof Function)) {
        throw new IllegalStateException("The Highlight.js bundle does not define " + FUNCTION_NAME);
      }
      scope = created;
    } catch (IOException | RuntimeException e) {
      throw new IllegalStateException("Could not initialize the Highlight.js Rhino engine", e);
    } finally {
      Context.exit();
    }
  }

  @Override
  public synchronized String highlight(String source, String language) {
    if (source == null) {
      throw new IllegalArgumentException("Source code cannot be null");
    }
    if (language == null || language.isBlank()) {
      return null;
    }
    Context cx = enterContext();
    try {
      Function function = (Function) scope.get(FUNCTION_NAME, scope);
      Object result = function.call(cx, scope, scope, new Object[]{source, language});
      if (result == null || Undefined.isUndefined(result)) {
        return null;
      }
      return Context.toString(result);
    } finally {
      Context.exit();
    }
  }

  private static Context enterContext() {
    Context cx = Context.enter();
    // Must be set before initStandardObjects for Symbol/Map/Set to be present.
    cx.setLanguageVersion(Context.VERSION_ES6);
    // Interpreted mode avoids Rhino's 64K per-method bytecode limit on this
    // ~1.2 MB script.
    cx.setInterpretedMode(true);
    return cx;
  }
}
```

### Task 6: Stop evaluating inline expressions inside non-Groovy fences

**Files:**
- Modify: `gmd-core/src/main/groovy/se/alipsa/gmd/core/GmdTemplateEngine.groovy:41,48-62,91`
- Test: `gmd-core/src/test/groovy/test/alipsa/groovy/gmd/GmdTemplateEngineTest.groovy`

The parser tracks only ```` ```{groovy ```` fences. Everything else falls through to `expandInlineVars`, so a ```` ```text ```` block containing ``literal `= 1+1` here`` came out as `literal 2 here` — verified. This makes it impossible to document gmd syntax in a gmd file and breaks shell snippets containing backticks.

**Scope.** This covers both CommonMark fenced forms — backtick and tilde — and tracks both the delimiter *character* and its *length*. Length matters: CommonMark closes a fence only with the same character at **at least** the opening length, so a four-backtick fence may legally contain three-backtick lines. That is not a hypothetical — `README.md` documents gmd by wrapping ```` ``` ````-fenced examples in a four-backtick block, and a length-blind scanner would treat the inner fence as the close and resume expanding inline expressions mid-example.

It deliberately does **not** cover four-space indented code blocks: recognising those correctly requires knowing whether the indentation is a code block or list continuation, which needs real block-level parsing rather than a line scanner.     /** Remove at most the three spaces CommonMark permits before a fence. */
    private static String fenceCandidate(String line) {
        int indent = 0
        while (indent < line.length() && indent < 3 && line.charAt(indent) == ' ') {
            indent++
        }
        return line.substring(indent)
    }

    /** Length of the leading run of {@code marker} characters, i.e. the fence width. */
    private static int fenceRunLength(String line, char marker) {
        int i = 0
        while (i < line.length() && line.charAt(i) == marker) {
            i++
        }
        return i
    }

    /** A closing fence has no info string or other non-whitespace suffix. */
    private static boolean isClosingFence(String line, char marker, int minimumWidth) {
        if (line.isEmpty() || line.charAt(0) != marker) {
            return false
        }
        int width = fenceRunLength(line, marker)
        return width >= minimumWidth && line.substring(width).trim().isEmpty()
    }

## The runtime bundle

`src/main/resources/highlightJs/highlight.js` is generated by `./buildBundle.sh` from the
untouched Highlight.js distribution in `source/highlightJs`. The script concatenates, in
order: `src/main/js/prelude.js`, the upstream core, all 192 upstream grammars, and
`src/main/js/wrapper.js` - then runs a single stock `@babel/preset-env` pass over the result.

That pass transpiles **syntax only**. Rhino already provides `Symbol`, `Map`, `Set`,
`Object.assign`, arrow functions, template literals, destructuring, generators and optional
chaining, so **no polyfills are injected and nothing is hand-edited**. Rhino cannot parse
`class` declarations, rest parameters, call spread, `for(const...of)` or `\p{...}` regex,
which is the entire reason the transpile exists.

The toolchain is pinned by `package.json` and `package-lock.json` and installed with
`npm ci`, so the output is byte-reproducible. `./buildBundle.sh --verify` regenerates to a
temp file and diffs against the committed bundle, exiting non-zero if it is stale. Maven
never runs any of this, so a normal build needs no Node.

To upgrade Highlight.js, replace `source/highlightJs` with a newer `@highlightjs/cdn-assets`
release, run `./buildBundle.sh`, and commit the result.

Highlight.js keeps mutable state in the shared Rhino scope, so `HighlightJsHighlighter`
synchronizes; unsynchronized concurrent use was observed to corrupt that state. The Context
runs in interpreted mode, which avoids Rhino's 64K per-method bytecode limit on a ~1.2 MB
script. Measured on JDK 21 with all 192 grammars: engine init 182-287 ms warm, highlight

## Consequences accepted with this plan

- **A generated file is committed.** `highlight.js` (~1.18 MB) lives in git. Unlike its predecessor it is fully reproducible: `npm ci` from a committed lockfile, byte-identical across runs, and `--verify` proves it is current. Nothing in it is hand-edited.
- **Regenerating needs Node 18+.** Only regeneration and the CI drift check need Node and `npm ci`; normal Maven builds and consumers need nothing beyond Maven and a JDK. The final verification proves the latter by moving `node_modules` aside.
- **Rhino sets an ES ceiling.** Future Highlight.js releases using newer syntax are handled automatically by `preset-env`; the residual risk is new *built-ins* Rhino lacks, which would need a polyfill in `prelude.js`. GraalJS remains the escape hatch — the `SyntaxHighlighter` interface allows swapping engines without touching callers, at a cost of about 66 MB.

## Deferred, deliberately not in this plan

- **Indented code blocks are not protected from inline expansion.** Task 6 covers backtick and tilde fences. Recognising four-space indented code requires distinguishing a code block from list continuation, which needs block-level parsing rather than a line scanner — a disproportionate change for a form that gmd's own output never produces. `indentedCodeBlocksAreAKnownGap` pins the current behaviour so it is documented rather than accidental.
- **Raw HTML blocks are not protected from inline expansion.** The Task 6 scanner does not parse block-level HTML, so fenced-code protection does not establish the boundaries of an HTML block. Add block-aware parsing and a regression test before changing this behaviour.
- **Complete HTML attribute escaping.** Task 2 quotes values so spaces are valid, but values containing `\"`, `&`, `<`, or `>` are not escaped. Defer a full escaping fix and compatibility review to a later task.
- **`gmdToHtml` overload naming.** The String overload returns a fragment while the File and Writer overloads write full documents. Renaming is a breaking API change; Task 3 documents the trap instead. Revisit for 4.0.
- **Inline expression parsing.** `` `=(.+?)` `` cannot handle a backtick inside the expression — `` `= "a`b" ` `` fails. Fixing this needs a real tokenizer, not a regex, and no user has hit it.
